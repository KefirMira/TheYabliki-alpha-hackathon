# Платежи и непрозрачные идентификаторы — v1.19.0b

Формат: UTF-8 (BOM допустим), разделитель `;`, заголовки в указанном порядке:

- payments: BENEFICIARY;PAYER;PAY_AMT;PAY_CNT;
- links: SYNTHETIC_F;CITY_NAME;RC_NAME;SYNTHETIC_U.

PAY_AMT — конечный неотрицательный Decimal, точно представимый NUMERIC(18,2),
без округления; PAY_CNT — целое 0..9223372036854775807. Идентификаторы обязательны,
без крайних пробелов/управляющих символов, максимум 128 символов. CITY_NAME и RC_NAME
могут быть пустыми, это непрозрачные текстовые значения (до 1024 символов), не роли.
Никакие валюты, периоды, единицы измерения не предполагаются.

Из backend, с установленными зависимостями backend:

```powershell
python -m dataset_import payments --file 'C:\private\df_Uid_payment_hack.csv'
python -m dataset_import links --file 'C:\private\df_Fid_Uid_link_hack.csv'
```

По умолчанию это dry-run без БД. Для подсчёта внешних идентификаторов добавьте
`--companies-file 'C:\private\df_Uid_data_hack.csv'`: справочник валидируется
импортёром профилей, конфликтные/ошибочные профили исключаются. Без этого параметра
число отсутствующих в справочнике идентификаторов неизвестно (`null`), не равно нулю.
Сверка с файлом — оценка, не утверждение о текущем содержимом какой-либо БД.

Отчёт содержит только количества, поля, номера физических строк и коды ошибок.
Первые 1000 диагностик сохраняются в отчёте, полный счётчик ошибок не ограничивается.
0 — проверка успешна; 2 — некорректные значения; 1 — ошибка структуры/кодировки/операции.
Неправильное число колонок или другой формат файла не угадывается и не исправляется.

Каждая запись сохраняется отдельно, включая точные повторы. Ключ строки:
`pulse-csv-row-v1:<kind>:<SHA256 файла>:<номер записи>`. Номер записи не зависит от
содержимого пары; одинаковые пары и суммы не суммируются и не объединяются.
Повтор того же файла не создаёт новых строк. Иное имя копии с теми же байтами
не меняет идентичность строк; происхождение хранит первоначальное имя файла.
Изменение байтов, включая порядок строк, BOM или переводы строк, означает другой снимок.

Миграция 007 не нужна: обе таблицы уже имеют UNIQUE(source_id), внешние текстовые
идентификаторы и source_data JSONB. BENEFICIARY соответствует source_company_id,
PAYER — payer_source_company_id. company_id заполняется только при точном совпадении
существующего companies.source_id; иначе остаётся NULL. Новые компании не создаются.

Для links используется существующая company_person_links: source_company_id хранит U,
legacy-поле source_person_id хранит **непрозрачный F**, не утверждая природу объекта.
person_id, role, relation_type остаются NULL; persons не заполняется. RC_NAME сохраняется
как текст в rc_name и исходном JSON, не преобразуется в роль. Потребители не должны
считать такую строку доказательством связи с физическим лицом. Уточнение семантики
источника и при необходимости отдельная нейтральная модель — будущая задача.

Все четыре исходных строковых значения, первоначальный basename файла (без пути),
SHA-256 файла/записи, номер записи и физических строк, источник и версия импортёра
сохраняются в source_data._external_csv_row_v1. Данные приватны; CSV, выгрузки БД и
приватные отчёты не публикуются в Git. Синтетические CSV тестов создаются во временной папке.

## Применение в изолированную PostgreSQL

Используется та же защита цели, что у [импортёра профилей](COMPANY_CSV_IMPORT.md):
`postgresql+asyncpg`, буквальный loopback 127.0.0.1/::1, явный порт, имя `test_*`,
совпадающий expected-database и комментарий БД `pulse:isolated-company-import:v1`.
Маркер устанавливает оператор только на заранее проверенной собственной тестовой БД.
Маркер или loopback-туннель сами по себе не доказывают изоляцию: shared/production
использовать запрещено. CLI не читает .env, не создаёт БД/таблицы и не ставит маркер.
Примените существующие schema → 002 → 003 → 004 → 005 → 006 до импорта.

DSN задаётся локально в DATASET_IMPORT_DATABASE_URL, не в командной строке,
исходниках или Git. DATABASE_URL и COMPANY_IMPORT_DATABASE_URL не используются.
После проверки dry-run и отдельного разрешения полного реального импорта:

```powershell
python -m dataset_import payments --file 'C:\private\df_Uid_payment_hack.csv' `
  --apply --confirm-isolated-import --target isolated `
  --expected-database test_company_import_demo

python -m dataset_import links --file 'C:\private\df_Fid_Uid_link_hack.csv' `
  --apply --confirm-isolated-import --target isolated `
  --expected-database test_company_import_demo
```

Любая ошибочная строка блокирует **весь файл**, частичный импорт здесь не поддерживается.
При ошибке SQL/проверки откатывается весь запуск. Ошибки не печатают исходные значения
или текст исключений драйвера. Автоматических повторов нет. При потере ответа после
commit состояние сначала проверяют; повтор того же файла идемпотентен.

Запись пакетная (1000 строк), без временных или постоянных новых таблиц.
Используются JSONB-параметры и INSERT ON CONFLICT DO NOTHING, затем отдельная проверка
совпадения записанных строк. Существующие строки никогда не перезаписываются.
Конфликт данных по техническому ключу останавливает и откатывает запуск.
Переименование идентичной копии не обновляет первоначальное имя в происхождении.

Один тип набора в одной БД допускает только один байтовый снимок. Изменённый SHA-256
блокируется кодом NEW_SNAPSHOT_REQUIRES_SEPARATE_DATABASE; удалять старые строки или
складывать новые поверх старых автоматически нельзя. Иначе изменённый файл мог бы
незаметно удвоить суммы, поскольку исходник не даёт устойчивого ID платежа/периода.
Новый снимок требует отдельной тестовой БД и отдельного решения о замене набора.
Два типа набора (payments и links) в одной тестовой БД совместимы.

Импорт на время транзакции блокирует конкурентные записи в соответствующую таблицу
(SHARE ROW EXCLUSIVE, ожидание до 10 с); чтение не блокируется. Это сериализует
проверку разных снимков. UNIQUE(source_id) дополнительно защищает каждую строку.
Длинная транзакция может удерживать блокировки и создавать WAL; ресурсы нужно проверить
до реального импорта. Ошибка/повтор может оставлять пропуски IDENTITY — это не потеря
исходных записей и не изменение их содержимого.

Профили, persons, новости, инсайты, analysis_runs и evidence импортёр не изменяет.
Если неизвестная компания появится позже, повтор не заполняет старый NULL company_id
автоматически: внешняя ссылка уже сохранена, согласование FK — отдельная операция.
Подсчёт неизвестных идентификаторов dry-run относится только к указанному справочнику.

Проверяйте created/unchanged/updated, число строк и уникальность технического source_id;
при повторе ожидается created=0, updated=0, unchanged=числу исходных строк.
Суммирование платежей возможно только после уточнения валюты, единиц, периода и природы
повторных пар. Пользовательское API для этих сырых наборов пока не добавлено.

## Безопасные тесты

```powershell
# Из корня репозитория, в подготовленном Python-окружении:
python -m pytest backend/tests/test_dataset_import.py -q
# Полный PostgreSQL-прогон создаёт новый проект и новый том:
powershell -NoProfile -ExecutionPolicy Bypass -File backend/tests/run-profile-tests.ps1 `
  -ComposeOverride 'C:\private\external-network.override.yml'
```

Интеграционные тесты используют только синтетические CSV. Нагрузочная проверка —
по 50 тысяч строк каждого типа, включая повторы, с повторным применением.
Фактические времена зависят от Docker, диска и размера атрибутов; это не гарантия
скорости полного реального файла. Тестовые контейнеры останавливаются с сохранением
томов; чужие ресурсы и frontend demo не используются.

## Результат предварительной проверки предоставленных файлов

Реальные CSV использованы только для dry-run, не для записи или тестовых фикстур.
Платежи: 1 380 585 корректных строк; 17 дополнительных строк повторных пар,
включая один точный повтор. Связи: 12 514 корректных строк, повторных пар нет;
11 120 различных F и 12 307 различных U. Пустые CITY_NAME/RC_NAME допустимы.

Относительно 85 513 допустимых профилей (12 конфликтующих строк исключены):
62 039 различных BENEFICIARY, 103 696 PAYER и 7 788 U из links отсутствуют
в справочнике. Это не повод создавать вымышленные профили или удалять строки.
Более ранний подсчёт по всем различным U, включая конфликтный, давал для платежей
на один внешний идентификатор меньше в каждой колонке.

Измерение на 50 000 синтетических строк: первый импорт payments 10,6 с,
links 10,8 с; повтор 8,5 и 7,8 с. Примерная скорость первого импорта —
4,6–4,7 тысяч строк/с. Это тест инструмента, не результат полного реального импорта.
Валидация использует множества хешей строк/пар и идентификаторов: потребление памяти
растёт с числом различных строк, хотя запись в БД ограничена пакетами по 1000.

# Серверная авторизация и доступ — v1.22.0

Срез предназначен для изолированного хакатонного стенда. Frontend не изменён:
старый demo-login больше не даёт доступа к HTTP API. Общего demo-токена и
конфигурационного флага отключения авторизации нет.

## Схема и политика

Применять `database/schema.sql`, затем миграции 002–007 по порядку.
`007_auth_access.sql` аддитивна: auth_users, auth_sessions, auth_user_companies,
auth_news_grants. Старые таблицы, ограничения глобальной идентичности новостей,
анализы и evidence не меняются. Повторное применение не меняет данные. Таблицы
создаются только SQL-runner, никогда ORM. `/ready` требует также четыре auth-таблицы.

Аккаунт не является persons или SYNTHETIC_F. Логин — нормализованный ASCII,
3–64 символа; пароль хранится как Argon2id (19 MiB, time_cost=2, parallelism=1,
случайная соль). Хеширование/проверка выполняются вне DB-сессии и event loop.
Сессия — отдельный случайный 256-битный Bearer-токен на один час. В БД хранится
только SHA-256 токена; токен возвращается один раз при login. Не передавать его
в query string, не сохранять в файлы/логи. Снаружи localhost обязателен HTTPS.

Каждый защищённый HTTP-запрос заново проверяет срок/отзыв сессии и активность
пользователя. Company-scoped маршруты проверяют membership; can_analyze отдельно
разрешает запись/анализ. Нет автоматического admin-доступа. Удаление membership
действует на следующий запрос; отзыв не отменяет уже начатую работу сервиса.
Auth DB-сессии закрываются до обращения к analyzer. Jobs/attempts, owner fencing,
COMPLETED-cache, atomic persistence, retry policy и внешний guard сохранены.

Пользовательская новость приватна по умолчанию: INSERT новости и grant автору
фиксируются одной транзакцией. Откат grant откатывает новость. Дубликат доступен
только при существующем grant; знание URL/внешнего ID не выдаёт grant. Недоступный
дубликат даёт общий ACCESS_DENIED без ID/метаданных/diagnostics. Глобальные URL и
source pair остаются уникальны: две приватные копии одного URL не создаются.
Сам факт различия успешного создания и отказа не обеспечивает скрытия существования
идентичности; это ограничение выбранной глобальной дедупликации, а не разрешение
на чтение записи.

Для saved-news анализа grant проверяется **до** чтения новости, claim и cache.
Лента и карточка тоже ограничены grant: два участника одной компании могут видеть
разные инсайты. Cursor применяется после ACL-фильтра, counts/next_cursor чужих
записей не раскрываются. Недоступная карточка даёт общий 403, включая отсутствие
строки; запрос чужой компании тоже 403. Историческим новостям/аккаунтам миграция
не назначает права. Старые анализы сохранены, но могут быть невидимы до явного
выделения доступа. Публичного grant/admin/retry endpoint нет.

Политика общих RSS-материалов и service identity ещё не реализована. Parser теперь
получит 401 без индивидуальной авторизации; запускать реальный сбор нельзя.
Не маркировать все EXTERNAL новости как публичные: UI тоже использует этот вид.

## HTTP

| Операция | Правило |
|---|---|
| POST `/api/auth/login` | JSON login/password → 200 access_token/token_type/expires_in; неверный логин и пароль одинаково 401; 422 не отражает тело/значения/имена лишних полей |
| GET `/api/me` | Bearer → user_id, login, companies (source_id, name, can_analyze); никаких credential hashes |
| POST `/api/auth/logout` | Bearer → 204, отзыв только текущей сессии |
| GET `/api/companies/{source_id}` | Сессия + membership |
| GET `/api/companies/{source_id}/insights[/{insight_id}]` | Сессия + membership + news grants в SQL-проекции |
| POST `/api/companies/{source_id}/analyses` | can_analyze; MANUAL-новость получает grant при успешном создании |
| POST `/api/companies/{source_id}/news/{news_id}/analyses` | can_analyze + news grant, в том числе для COMPLETED |
| POST `/api/news` | Сессия; новая новость приватна; duplicate не выдаёт чужие данные |
| POST `/api/analyze`, `/api/analyze-rag`, `/api/analyze-company` | Без сессии 401; с сессией 403 — legacy платный обход закрыт |
| `/health`, `/ready`, `/docs`, `/openapi.json` | Публичные операционные проверки/схема без секретов; readiness не вызывает провайдера |

Нет токена/неверный/истёкший/отозванный токен: 401 с WWW-Authenticate: Bearer.
Нет права: 403 ACCESS_DENIED. БД недоступна: 503, без fallback к анонимному доступу.
AI_MODE=demo продолжает запрещать AI после auth; full не снимает
COMPANY_CONTEXT_EXTERNAL_TRANSFER_BLOCKED. Auth-успех не разрешает внешнюю передачу.
Ответы `/api/*` имеют Cache-Control: no-store. Существующие успешные domain JSON
сохраняются; обязательный Bearer и новые 401/403 — документированное изменение
security-контракта. OpenAPI содержит 14 операций.

## Ограничение попыток

Процессный bounded limiter: до 5 попыток за 15 минут для нормализованного логина
независимо от IP и до 30 для peer IP. Считаются и успешные попытки. Неизвестный
пользователь проходит dummy Argon2-проверку. Ответ превышения — 429, Retry-After.
В памяти только salted hashes bucket keys; максимум 10000 buckets, переполнение
закрывает новые входы до освобождения окна. Лимитер не хранит пароли.
Одновременно выполняются не более четырёх Argon2-проверок; очередь не накапливается.
Отмена HTTP-задачи не освобождает слот до фактического завершения hash worker.

Это **один backend worker**. Для нескольких процессов/реплик нужен общий limiter
на proxy/Redis/PostgreSQL; перезапуск процесса сбрасывает окна. Не считать текущий
лимитер production-защитой от распределённого brute force. Не доверять произвольному
X-Forwarded-For; доверенные proxy настраиваются при размещении отдельно.

## Изолированные синтетические аккаунты

`backend/auth_demo.py` создаёт один аккаунт за транзакцию, без сброса существующих
паролей. Нужны отдельная тестовая БД `test_*`, loopback PostgreSQL с явным портом,
ожидаемое имя БД и заранее проверенный владельцем marker-комментарий
`pulse:isolated-auth-demo:v1`. CLI переиспользует адресный guard CSV-импортера,
но проверяет **свой** marker. Он не подходит для общей/production БД и не выдаёт
права на импортированные компании или исторические новости.

В уже созданной и проверенной изолированной БД применить 001–007; только затем
владелец ставит marker командой `COMMENT ON DATABASE test_auth_demo IS
'pulse:isolated-auth-demo:v1';`. Не помечать таким образом существующую общую БД.
В `AUTH_DEMO_DATABASE_URL` передать DSN этой БД локально, не печатая и не коммитя.

Из backend:

```powershell
python -B -m auth_demo --confirm-isolated --expected-database test_auth_demo --login synthetic-alice --company SYNTH-AUTH-A
python -B -m auth_demo --confirm-isolated --expected-database test_auth_demo --login synthetic-bob --company SYNTH-AUTH-B
```

Пароли 12–256 символов вводятся через getpass дважды, не argv/env. CLI создаёт
только SYNTH-AUTH-A/B с source_data marker, не переиспользует произвольную
компанию. Повторный login name вызывает ошибку и полный откат, а не password reset.
Токенов CLI не создаёт/не печатает. Для проверки получить их через login API;
в Swagger использовать Authorize → индивидуальный токен. Demo API-аккаунты не
создаются автоматически при старте приложения или миграции.

## Frontend и развёртывание

React пока не изменён. Требуется отдельный срез login API → `/api/me` → Bearer в
fetch → 401/403/logout. Хранить токен в памяти, не в URL/localStorage; после
перезагрузки повторный login допустим для MVP. Не доверять VITE_DEMO_ACCOUNTS и
current_company_id как источнику прав. Старый demo frontend получит 401 — это
ожидаемое закрытие незащищённого API, не повод добавлять общий токен/обход.

Compose монтирует 007 для **нового** тома; restart старого не применяет миграцию.
Нужен явный SQL upgrade выбранной изолированной БД и rebuild backend. Не удалять
том ради upgrade. Подготовленный аудит FRONTEND_BACKEND_AUDIT.md остаётся снимком
до этого изменения и не редактируется/не коммитится данным срезом.

## Тестовая граница

Новые `test_auth_*` используют настоящую аутентификацию и ACL в изолированной PG,
синтетические пароли/компании и fake analyzer. Старые domain/API-тесты получают
явные dependency overrides только в tests/conftest.py, чтобы проверять прежнюю
бизнес-логику отдельно от auth. Это не runtime-конфигурация и не env bypass.
Полный регресс обязателен вместе с новыми auth-тестами, а не вместо них.

PREPARATION_FAILED из предыдущего аудита остаётся открытым диагностическим
вопросом; эта авторизация не объявляет его исправленным. Долговременный security
audit log, управление пользователями, password recovery, реальные SMS/email,
банковская авторизация и shared RSS ACL в этот срез не входят.

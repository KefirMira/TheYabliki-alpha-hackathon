# Детерминированные упоминания компаний — v1.17.0

Сопоставление читает сохранённые `news_articles.title/content` и справочник `companies`.
LLM, RSS, платный анализ, пользовательская авторизация и frontend не участвуют.
Один запуск CLI обрабатывает одну новость; публичного HTTP endpoint нет.
Доступ ограничивается доступом оператора к компьютеру и учётной записи PostgreSQL.
Не передавайте административные реквизиты parser или frontend.

## Алгоритм и ограничения

- ИНН: точные ASCII-цифры длиной 10/12, ОГРН: 13/15; границы не допускают
  вхождения внутрь другого числа или слова. Контрольная сумма и действительность
  регистрации не проверяются. Дубли идентификатора в справочнике дают неоднозначность.
- Названия: NFKC, casefold, `ё → е`, токены с границами слов. Поддерживаются
  кавычки, пробелы, дефисы, краткие и полные формы ООО/АО/ПАО/ОАО/ЗАО/ИП.
  Несовпадающая явно указанная организационная форма даёт неоднозначность.
  Самое длинное известное название подавляет вложенное короткое название.
  Разные предложения не склеиваются в одно название.
- Консервативный порог: минимум 10 символов в токенах названия; однословное
  название — минимум 10 символов. Название только из распространённых слов
  встроенного списка недостаточно. Это правило снижает ложные совпадения,
  но пропускает настоящие короткие названия. Список не является полным словарём
  общеупотребительных слов: совпадение — текстовое упоминание, не доказательство
  юридической идентичности. Падежи, транслитерация и нечёткий поиск отсутствуют.
- Техническое название, равное `source_id`, игнорируется. Отрасль, регион,
  платежи и произвольный `source_data` не используются.
- Альтернативы читаются **только** из `company_verified_names`. Оператор должен
  проверить название до добавления, указать `verified_by` и `provenance`.
  Наличие заполненного поля само по себе не проверяет источник; это обязанность
  администратора. Автоматического импорта неподтверждённых альтернатив нет.
- Если хотя бы одно обнаруженное упоминание неоднозначно, весь запуск имеет
  `AMBIGUOUS`, `matched_company_ids=[]`. Даже однозначные кандидаты в таком запуске
  остаются только материалом ручной проверки. Уникальный ИНН не используется для
  догадки, к какому из неоднозначных названий в другом месте текста он относится.
- `MATCHED`: все найденные упоминания однозначны, возможно несколько компаний.
  `NO_MATCH`: известных упоминаний нет. Это не означает нерелевантность новости.

## Данные и повторная обработка

Миграция 006 добавляет три таблицы, не меняя 001–005 и существующие записи:

| Таблица | Назначение |
|---|---|
| `company_verified_names` | Проверенные оператором альтернативы, источник и автор проверки |
| `news_company_match_runs` | Версия алгоритма, статус, SHA-256 текста и справочника, снимок title/content |
| `news_company_match_candidates` | Кандидаты с FK компании и запуска, снимок компании и массив evidence |

Кандидаты **не являются** связями для автоматического AI-анализа. Использовать их
как однозначные можно только при статусе родительского запуска `MATCHED`.
В evidence записаны INN/OGRN/NAME, причина, поле title/content, точная цитата,
start/end (индексы Unicode code points Python, конец исключён), использованные
названия и их происхождение. JavaScript использует UTF-16: frontend должен
учитывать отличие индексов для символов вне BMP. Цитату проверять по сохранённому
`news_snapshot`, а не по возможной новой версии новости.

Уникальный ключ версии: `(news_id, algorithm_version, news_hash, dictionary_hash)`.
Для одной новости используется `FOR UPDATE`: параллельные процессы сериализуются;
все результаты и кандидаты сохраняются одной транзакцией. Сбой откатывает всё.
Timeout блокировки — 5 секунд; повторить команду вручную безопасно.
Справочник и альтернативы читаются одним SQL statement (единый снимок).
Изменение имени/ИНН/ОГРН/проверенных альтернатив меняет отпечаток; новый запуск
сохраняет отдельную версию, старую можно просмотреть по `--run-id`. Возврат к
прежнему снимку переиспользует старую версию. `show` без `--run-id` показывает
последнюю **созданную** версию; используйте ID из `match` для точного результата.

Полный справочник загружается в память на каждый запуск; trie используется для
названий, цифровые токены сканируются один раз. Большие справочники требуют
замеров производительности и будущего кэша с корректной инвалидизацией.
Предусмотрено хранение истории, но не автоматическое применение новой версии ко
всем новостям, не ручное разрешение неоднозначности и не срок хранения истории.

## Миграция и запуск

Порядок: `schema.sql → 002 → 003 → 004 → 005 → 006 → синтетические фикстуры`.
Новые demo-тома и тестовые runner применяют 006. Старые тома автоматически не
обновляются; `/ready` вернёт 503 до явного применения 006. Проверка read-only
сверяет таблицы, колонки, ограничения и индексы. Повтор миграции допускается только
при точном совпадении определений; расхождения не исправляются автоматически.

Перед обновлением **собственного тестового** тома: остановить его backend, проверить
Compose project/volume и текущую БД, сохранить резервную копию, убедиться, что
объектов 006 ещё нет либо они полностью соответствуют миграции. Затем вручную:

```powershell
Get-Content -Raw -Encoding UTF8 database/migrations/006_news_company_matching.sql |
  docker compose -p <свой-проект> -f compose.frontend.yml exec -T postgres psql -X -v ON_ERROR_STOP=1 -U pulse_demo -d pulse_demo
```

При external network использовать тот же `-f <override>` во всех Compose-командах.
Команда не предназначена для общей/production-БД. Откат до COMMIT автоматический;
после COMMIT предпочитайте вернуть совместимое приложение и сохранить таблицы.
Удаление новых таблиц уничтожит историю сопоставлений и требует отдельного решения
и backup. Down-миграция автоматически не выполняется.

Для CLI из корня репозитория (PowerShell, без автоматического чтения `.env`):

```powershell
$env:PYTHONPATH = (Resolve-Path backend).Path
# DATABASE_URL задаётся оператором для изолированной PostgreSQL, postgresql+asyncpg://...
.venv/Scripts/python.exe -m news_matching_admin match --news-id 1 --confirm-write
.venv/Scripts/python.exe -m news_matching_admin show --news-id 1
.venv/Scripts/python.exe -m news_matching_admin show --news-id 1 --run-id 1
```

Коды завершения: 0 — результат прочитан/сохранён, 1 — ошибка БД или отсутствие
новости/результата, 2 — неверные аргументы. Ошибки не раскрывают DSN и SQL.

## Проверка на demo

Новый demo-том содержит проверенную **вымышленную** альтернативу компании DEMO-001:
«Синтетическая северная пекарня». Приём синтетической новости:

```powershell
$body = @{title='Синтетическая северная пекарня'; content='Полностью вымышленный материал.';
  source_name='synthetic-demo'; source_id='SYNTH-MATCH-001'} | ConvertTo-Json
$news = Invoke-RestMethod http://localhost:8000/api/news -Method Post -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($body))
docker compose -p <свой-проект> -f compose.frontend.yml exec -T backend python -m news_matching_admin match --news-id $news.news_id --confirm-write
```

Ожидается `MATCHED`, один кандидат DEMO-001, цитата заголовка. Повтор возвращает
тот же `id` и `reused=true`. Платный AI в demo остаётся заблокирован.
Текущие старые demo-тома этой новой альтернативы не содержат: добавление фикстур
на них автоматически не выполняется.

Тесты: `backend/tests/run-profile-tests.ps1 -ComposeOverride <внешний-override>`
и `database/tests/run.ps1 -ComposeOverride <внешний-override>`. Каждый запуск
использует новый собственный том; существующие ресурсы не удаляются.

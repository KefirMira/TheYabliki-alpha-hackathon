# Передача PostgreSQL — «Пульс бизнеса»

PostgreSQL 16, 13 прикладных таблиц. Пакет содержит только схему, миграции и полностью синтетические тестовые данные. AI-модуль не включён в этот PR и не изменён.

## Данные и публикация

Разрешение на публикацию данных хакатона не подтверждено. Реальные CSV и оригинальный seed.sql НЕ публикуются в Git. Если исходные файлы сохранены локально, размещать их в игнорируемом database/private/; эта папка не монтируется в тестовый контейнер.
Фикстуры database/tests/fixtures/base.sql и pulse.sql придуманы специально: идентификаторы SYNTH-*, условные компании, люди, новости, суммы и доказательства не скопированы из CSV. URL example.invalid не ведёт на реальный источник.
Для реальных данных нужен отдельный импорт владельцем БД: staging, проверка конфликтов идентификаторов, повторных записей, неизвестных контрагентов и стабильных ключей. Синтетические фикстуры не запускать в командной рабочей БД.

## Состав и порядок

1. database/schema.sql — исходная схема без изменений.
2. database/migrations/002_pulse_features.sql — исходное расширение без изменений.
3. database/migrations/003_integrity.sql — уровни, JSONB и согласованность компании результата/запуска.

Применять через psql -X -v ON_ERROR_STOP=1 -f <file>. SQL содержит собственные транзакции; не добавлять psql -1.
002/003 допускают повторное применение к ожидаемой структуре, но не исправляют несовпадающие типы ранее созданных объектов. Журнал миграций пока не реализован — его выбирает владелец БД. Перед применением к существующим данным нужны backup, проверка восстановления и окно DDL-блокировок. В 003 lock_timeout=10s.

## Изолированный тест

Из корня репозитория (PowerShell):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File database/tests/run.ps1
```

Требования: Docker Desktop Linux containers, Compose v2 с up --wait. Python, pip, LLM и CSV не нужны.
Скрипт создаёт случайное имя проекта и собственные контейнер/том, использует postgres:16 и 127.0.0.1:55433. Образ скачивается при отсутствии. При занятом порте заранее задать $env:DB_TEST_PORT='55434'; чужие контейнеры не останавливаются.
DB_TEST_PASSWORD генерируется в памяти либо берётся из окружения. database/.env.example — только шаблон, автоматически не загружается. Не печатать docker compose config без --quiet: он раскрывает пароль.
Порядок теста: schema → синтетическая base fixture → контрольные суммы → 002 → 003 → pulse fixture → тесты → повтор 002/003 → тесты → сравнение сумм всех 13 таблиц.
Ожидается: компании/люди/связи/платежи — по 2 строки, остальные 9 таблиц — по 1 строке. Проверочные строки создаются и откатываются; identity-счётчики могут продвинуться. Негативные тесты сверяют SQLSTATE и имя ограничения (для триггеров — сообщение); FK проверяются UPDATE одной строки по id, чтобы не задевать UNIQUE других строк.
После теста собственный контейнер останавливается, том сохраняется. Каждый запуск создаёт новый том. Очистка не автоматизирована; down -v и volume prune не использовать без отдельного согласования.
Имя проекта выводится в начале/конце. Возобновление: задать DB_TEST_PASSWORD для проверки Compose и выполнить docker compose -p <имя> -f database/compose.test.yml start. У уже созданной БД пароль от этого не меняется. Локальный доступ через exec -T postgres psql -U audit_user -d theyabliki_test.

## Контракт

- relevance_level, impact_level, evidence_strength: high / medium / low / unknown или SQL NULL.
- insight_kind: risk / opportunity / mixed / information или SQL NULL. Текущий AI это поле не возвращает.
- facts, risks, opportunities, recommendations, scenarios, source_snapshot, supporting_data: JSON-массивы.
- validation, structured_context, extracted_metadata: JSON-объекты. Форму элементов проверяет API.
- analysis_runs.company_id=NULL сохраняет возможность запуска для разных компаний. Если компания указана, результаты обязаны совпадать с ней. Триггеры проверяют изменения обеих сторон; старое несоответствие останавливает миграцию. FOR SHARE сериализует изменение родителя; при deadlock приложение повторяет транзакцию.
- updated_at не обновляется автоматически, это обязанность слоя записи.

## Подключение AI отдельным PR

Найти companies по source_id; внутренний id использовать в FK. CompanyProfile получает source_id, industry, region, revenue; credit_exposure=None, в исходных данных его нет.
Сохранить новость, запуск, результат и evidence транзакционно: relevance → relevance_level, summary → impact_summary; списки и validation → JSONB; sources → snapshot и evidence.
sources.id локален внутри ответа, а не ID каталога. TF-IDF score не является вероятностью. Отсутствующие levels, facts/scenarios не выдумывать. Дату точности месяца нельзя преобразовывать в произвольный день. Валюта и период выручки требуют уточнения.

## Дальнейшая работа владельца

Миграционный инструмент; отдельный импорт реальных файлов; аутентификация и проверка доступа по user_key; проверка формата SHA-256 и метаданных документов; обновление updated_at; конкурентные тесты и backup/restore. RLS не настроена. Хранение файлов — вне БД.
Новый PR должен содержать только инфраструктуру и документацию, без восьми AI-коммитов. Не заменять Compose других участников; переносить настройки через согласованный PR с сохранением томов.

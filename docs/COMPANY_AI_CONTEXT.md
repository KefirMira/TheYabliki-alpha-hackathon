# Контекст компании для AI — v1.20.0

Серверная подготовка контекста не вызывает LLM, не изменяет данные, не создаёт
таблицы и не отправляет source_data внешним сервисам. Максимум — 10 000 байт UTF-8.
Слишком длинное/некорректное поле исключается с отметкой missing, не обрезается
до потенциально другого смысла. Идентификаторы и строки платежей не попадают в контекст.

Структура `company-context-v1`:

- facts: отрасль, регион, выручка строкой Decimal с year/currency/unit, клиентский
  статус; из разрешённых полей импортированного CSV — ОКВЭД, интервалы FNS/СПАРК,
  признаки РКО/гарантий/кредитного продукта/лизинга/депозита/зарплатного проекта,
  факторинга и ВЭД. Каждый факт содержит origin. ОКВЭД передаётся только при
  совпадении текущей отрасли с отраслью в том же CSV-профиле.
- computed.payment_structure: число исходных строк и различных контрагентов
  отдельно по входящему (CSV BENEFICIARY) и исходящему (CSV PAYER) направлению.
  Повторы сохраняются, контрагенты без профилей учитываются. Самоссылка появляется
  в обоих направлениях. Нет суммирования PAY_AMT или PAY_CNT.
- missing: не полученные сведения; ноль строк не доказывает отсутствие платежей.
- excluded: намеренно не переданные поля, в том числе имена/ИНН/ОГРН, идентификаторы
  компании и контрагентов, суммы, исходные записи и JSON, хеши/имена файлов, связи F–U.
- model_assumptions: пустой список при подготовке, не источник фактов.

CSV — утверждения исходной выгрузки, а не независимая проверка актуального состояния
компании. Год выручки может быть известен из companies; валюту и единицы текущая
схема не подтверждает. Они остаются null даже при наличии суммы. Интервалы не
превращаются в точную численность. CSV-признак банковского продукта не доказывает
долг, действующий договор или размер обязательств; ВЭД не устанавливает направление
торговли, страны, товары или операции. SYNTHETIC_F вообще не интерпретируется.

Один SQL-запрос возвращает только ограниченную проекцию и агрегаты в одном snapshot.
После существующего поиска компании это один дополнительный запрос, независимо от
числа контрагентов. Используются существующие индексы source_company_id и
payer_source_company_id. Только строки с происхождением df_Uid_payment_hack входят
в показатели; наличие снимка не означает полноту/актуальность всей платёжной истории.
Никакие миграции не нужны. Метрики не являются оборотом, прибылью, долгом, количеством
операций, концентрацией сумм или достоверностью прогноза.

## Защита внешней передачи

DB-контекст по умолчанию запрещён для внешнего LLM-шлюза. HTTP/ENV-флага обхода нет.
Тесты используют только синтетические данные и явно подставленные локальные fake
анализаторы. Следующий этап реального применения требует отдельного решения об
обработке данных: согласованного локального анализатора либо разрешённой передачи
минимального набора провайдеру. Наличие API-ключа само по себе не является разрешением.

Структурная валидация и эвристические предупреждения не доказывают достоверность
модельного ответа; фактическая точность и качество рекомендаций требуют ручной оценки.

## Подключение и совместимость

`CompanyAnalysisService` загружает контекст в начальной короткой транзакции,
прикрепляя его к приватному серверному атрибуту `CompanyProfile._ai_context`.
Атрибут не входит в JSON, Pydantic/OpenAPI и не принимается из HTTP-запроса.
После commit сессия закрывается; во время анализатора соединение не удерживается.
Публичные схемы успешных ответов, evidence и GET истории не менялись.

Оба POST `/api/companies/{source_id}/analyses` и
`/api/companies/{source_id}/news/{news_id}/analyses` используют новый контекст.
При стандартном внешнем анализаторе свежий анализ возвращает **503** с кодом
`COMPANY_CONTEXT_EXTERNAL_TRANSFER_BLOCKED`: подготовленный контекст не покидает
backend, запуск/новость не создаются, предварительный claim откатывается.
Это сознательное ограничение v1.20.0: реальная CSV-информация не должна попасть
во внешний шлюз даже при наличии ключа. Существующий COMPLETED возвращается
как прежде (200) без загрузки контекста и без AI; RUNNING/retry сохраняют правила 409.
В demo прежняя блокировка срабатывает раньше сервиса.

Legacy `/api/analyze-company` по-прежнему работает с переданным клиентом профилем,
не обращается к PostgreSQL и не получает CSV/платежи. Это не универсальный DLP:
клиент сам отвечает за содержимое legacy-ввода. Сервисная dependency-инъекция
анализатора и `_local_rag` — доверенные программные точки для локального fake,
не параметры HTTP и не разрешение подключать внешний обработчик закрытых данных.

Базовый JSON-промпт и RAG system prompt сохранены. Только серверный контекст
использует отдельный блок `CONTEXT_RULES`, поскольку старый промпт не объяснял
неизвестные единицы выручки и семантику счётчиков. Новая версия сохраняемого
промпта — `company-context-v1`. Evaluation-хеш personalization_service обновлён
из-за интеграции; тест сравнивает исходный legacy-промпт и RAG messages буквально.
Оценочный CLI по-прежнему использует legacy-профиль без DB-контекста.

## Воспроизводимые проверки

Синтетические тесты: `backend/tests/test_company_context_unit.py`,
`test_company_context_personalization.py`, `test_company_context_integration.py`.
PostgreSQL-тесты запускаются общим `backend/tests/run-profile-tests.ps1` с
параметром `-ComposeOverride` для внешней тестовой сети, если пул Docker исчерпан.
Нужны установленные тестовые зависимости; тесты не используют реальные CSV.

Проверяются whitelist/ограничение 10 000 байт, Decimal, пропуски, разные отрасли
и продукты, одинаковая новость, повторы платёжных пар, внешние контрагенты,
неизменность компаний, сохранение результатов/evidence, повтор COMPLETED,
освобождение соединений, отсутствие SDK-вызова и HTTP 503 без утечки данных.
Нагрузочный тест создаёт 100 000 синтетических строк и 1002 компании, делает
три чтения с ровно тремя SQL-запросами. Это проверка отсутствия N+1 и локальный
ориентир времени, а не SLA или измерение на полном реальном наборе.

Следующий этап: согласовать доверенный способ локального выполнения модели или
правила разрешённой минимальной передачи провайдеру, затем отдельно проверить
качество персонализации. До этого внешний платный путь с DB-контекстом закрыт.

Проверка v1.20.0: полный безопасный прогон **611 passed, 0 skipped**, включая
PostgreSQL и повторное применение существующих миграций. Отдельный замер нового
нагрузочного теста: три чтения за 4,390 с, три SQL-запроса на 100 000 строк.
SDK и внешняя сеть блокировались. Использованы свежие отдельные тестовые тома
на существующей external-сети; контейнеры остановлены, тома/сети сохранены.
Реальные данные для этих тестов не использовались; качество реальной LLM не оценено.
Отдельный снимок AI-контекста пока не сохраняется: агрегаты отражают состояние
данных на момент чтения, а версия промпта сама по себе не обеспечивает точного
воспроизведения контекста после изменения справочника/платёжного набора.

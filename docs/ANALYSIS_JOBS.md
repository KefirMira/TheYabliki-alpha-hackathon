# Защищённый анализ сохранённых новостей — v1.15.0

Область: POST /api/companies/{source_id}/news/{news_id}/analyses. Одна строка задания на пару, максимум две попытки. Статус хранится в analysis_runs; попытка содержит владельца, срок проверки, разрешение retry и исходный JSON ответа. LLM вызывается после commit claim и закрытия session. Завершение блокирует то же задание и проверяет владельца. Сохранение результата/evidence/payload/COMPLETED атомарно.

## Ответы

201 — новый результат. 200 — сохранённый COMPLETED с тем же JSON, без AI. 409 ANALYSIS_ALREADY_RUNNING — уже выполняется; ANALYSIS_REVIEW_REQUIRED — просрочено/неопределённость; ANALYSIS_RETRY_REQUIRED — FAILED без разрешения; ANALYSIS_ATTEMPT_LIMIT_REACHED — лимит; ANALYSIS_ATTEMPT_CLOSED — поздний исполнитель. Остальные 404/422/502/503 сохранены. При ошибке связи с БД нельзя считать запуск отсутствующим или FAILED без подтверждения. Повтор запроса безопасно проверяет состояние.

## Проверка зависаний и ручной retry

Публичного административного endpoint нет. Команды выполняет доверенный оператор локально из backend, с DATABASE_URL из окружения. CLI не читает .env и не импортирует AI. Не передавайте DSN как аргумент командной строки.

```powershell
cd backend
python -m analysis_admin inspect
python -m analysis_admin close --company-source-id SYNTH-COMPANY-A --news-id 1 --run-id 7 --actor operator --reason "Проверено завершение старого исполнителя и провайдера" --confirm-worker-stopped --confirm-provider-finished
python -m analysis_admin approve-retry --company-source-id SYNTH-COMPANY-A --news-id 1 --run-id 7 --actor operator --reason "Разрешена вторая попытка после проверки" --confirm-worker-stopped --confirm-provider-finished
```

inspect — read-only, до 100 просроченных RUNNING, без закрытия и перезапуска. close переводит конкретную текущую RUNNING в FAILED/REVIEW_REQUIRED. approve-retry разрешает следующую попытку только после FAILED, не запускает AI и не сбрасывает счётчик. Следующий POST создаёт новый analysis_run. Одновременные POST не создают несколько вторых попыток. Указание старого run_id отклоняется.

**Оба подтверждения являются ответственным заявлением оператора**, а не автоматическим доказательством. Сначала подтвердите прекращение старого исполнителя и удалённой обработки. Если провайдер не позволяет выяснить исход запроса, оставляйте пару заблокированной. Не используйте срок 180 секунд как автоматическое разрешение retry. Новая попытка после неопределённого запроса может привести к дополнительному списанию, даже если локальная конкурентность исключена.

В MVP все ошибки после dispatch требуют ручной проверки; автоматического retry нет. Защищённый SDK: max_retries=0, timeout=120 секунд; общий timeout=150 секунд. Невалидный AI-ответ также расходует попытку. Ограничение двух попыток не является глобальным денежным бюджетом: разные пары имеют независимые лимиты. Повторный анализ после изменения модели/профиля/корпуса не открывается автоматически.

Demo блокирует AI до сервиса. Ручной POST и legacy LLM API сохраняют прежний контракт и не получают дедупликацию по тексту. Доступ к ним и к платному POST нужно ограничить общей авторизацией до публичного развёртывания.


## История и порядок обновления

005 не переписывает старые строки. Под блокировкой пары первый POST может зарегистрировать **один** корректный исторический COMPLETED и вернуть его с HTTP 200 без AI. Восстанавливается существующий CreatedCompanyAnalysis по сохранённым полям; evidence не изменяются. Время reserved_at импортированной попытки — время регистрации, не выдуманное время старого LLM-вызова. Если у пары несколько результатов, один запуск связан с несколькими результатами, компания не совпадает или payload невалиден, возвращается ANALYSIS_HISTORY_AMBIGUOUS/INVALID. Ничего автоматически не удаляется, не выбирается и не дополняется.

Не связанные с попытками старые NEWS RUNNING/FAILED/PENDING и COMPLETED без результата нельзя достоверно сопоставить с news_id. Они блокируют новый платный claim соответствующей компании с ANALYSIS_LEGACY_RUN_REVIEW_REQUIRED. Старый NEWS-запуск с company_id=NULL блокирует новый платный claim для всех компаний, поскольку его принадлежность неизвестна. Такие данные разбирают отдельно, не через retry CLI новых заданий. Подмена исторических полей для обхода защиты запрещена.

Порядок локального/будущего согласованного развёртывания:

1. Остановить старые экземпляры backend и дождаться/разобрать выполняющиеся запросы. Смешанный запуск старого и нового обработчиков не поддерживается: старая версия не соблюдает блокировку заданий.
2. Сделать резервную копию существующей БД и проверить схему/историю read-only запросами. На этом этапе проекта общая БД не используется.
3. Применить schema.sql → 002 → 003 → 004 → 005. На существующем томе выполнить только ещё не применённые миграции вручную, например `docker compose -f compose.frontend.yml exec -T postgres psql -X -v ON_ERROR_STOP=1 -U pulse_demo -d pulse_demo -f /docker-entrypoint-initdb.d/005_saved_news_analysis_jobs.sql` после проверки соответствующего проекта и mount. Никакого down -v.
4. Запустить новый backend, проверить /health, /ready и синтетический smoke. Старые записи регистрируются при запросе, а не массово переписываются миграцией.
5. Не откатывать backend к старому платному пути при активных заданиях: он обходит защиту. Откат требует остановки платных операций и отдельного разбора; новые таблицы, историю и evidence автоматически не удалять.

Новая пустая demo-БД получает 005 до синтетических fixtures. SQL-runner проверяет 15 таблиц и replay. /ready читает определения 004 и 005 без DDL. Проверка строго рассчитана на PostgreSQL 16 и стандартный search_path с public; несовпадение требует расследования, не автоматического ремонта.

Ограничение JSONB: replay сохраняет значения JSON-ответа, но не порядок ключей/пробелы исходного HTTP-представления. Независимые компании имеют независимые задания, попытки и результаты.


## Итог проверки v1.15.0

- Полный безопасный pytest backend + parser: **382 passed, 0 skipped** на PostgreSQL 16.15; SDK LLM и внешняя сеть заблокированы. Есть прежнее предупреждение Starlette/httpx.
- SQL-runner: 15 таблиц, replay 002–005, FK/CHECK и неизменность контрольных сумм синтетической истории — успешно.
- Восемь POST одной пары, независимые соединения, две компании, replay COMPLETED, FAILED/retry/лимит, поздний результат, зависание, timeout, потеря HTTP-ответа и подтверждения commit — проверены с fake AI.
- Регистрация истории сохраняет все старые строки, не выбирает между неоднозначными результатами, не вызывает LLM. Повреждённая/отсутствующая 005 даёт /ready=503 даже в read-only транзакции.
- Docker smoke — успешно, включая повтор 004/005, CORS и demo-блокировку. Использован локальный образ зависимостей и read-only текущие исходники, подтверждённые manifest из 51 файла; новая сборка образа с установкой зависимостей не выполнялась.
- Тестовая сеть: theyabliki-db-check-1a832d244c5f_default (external). Финальный pytest-том: theyabliki-profile-664e98264f23_audit_data. Smoke-том: pulse-v115-smoke-1c328541df_demo_pgdata. Это новые отдельные тома; контейнеры остановлены, тома/сети не удалены.
